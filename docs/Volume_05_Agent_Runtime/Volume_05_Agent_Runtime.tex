\chapter{Agent Runtime}
\label{cha:agent-runtime}

This volume specifies the \emph{agent runtime}---the execution environment that carries out query plans, orchestrates tool calls, manages conversation state, and streams results. The runtime is the bridge between the Query Planner (Vol.~07) and the external world (API, CLI, LLM providers).

\section{Design Goals}
\label{sec:runtime:goals}

\begin{designprinciple}[Stateless Execution]
Each query execution is a self-contained episode. No persistent agent state across queries; all context is passed explicitly in the plan and conversation history.
\end{designprinciple}

\begin{designprinciple}[Tool-First Architecture]
LLMs are not the primary actors; tools are. The LLM plans and decides; tools execute deterministically. This inverts the typical ``agent = LLM + tools'' model.
\end{designprinciple}

\begin{designprinciple}[Streaming by Default]
All long-running operations (search, synthesis, tool calls) stream partial results. The API responds with Server-Sent Events (SSE) or WebSocket frames.
\end{designprinciple}

\begin{designprinciple}[Budget Enforcement]
Every execution has configurable budgets: token budget, time budget, tool call budget, cost budget. Exceeding any budget terminates with a partial result.
\end{designprinciple}

\begin{designprinciple}[Observability Native]
Every decision (plan step, tool choice, retrieval result, synthesis token) is logged with structured traces. OpenTelemetry compatible.
\end{designprinciple}

\subsection{Core Components}
\label{sec:runtime:components}

\begin{itemize}
  \item \textbf{Plan Executor}: Traverses the query plan DAG, executes nodes in topological order, handles parallelism and dependencies.
  \item \textbf{Tool Registry}: Maps tool names to implementations, handles invocation, timeouts, retries, and result normalization.
  \item \textbf{LLM Client}: Abstracts LLM providers (local: llama.cpp, vLLM, ollama; remote: OpenAI, Anthropic, etc.) with unified streaming interface.
  \item \textbf{State Manager}: Maintains scratchpad, conversation history, intermediate results, and budget counters.
  \item \textbf{Stream Handler}: Emits SSE/WebSocket events for partial results, progress, errors, and final answer.
\end{itemize}

\subsection{Query Plan Structure}
\label{sec:runtime:plan-structure}

The planner (Vol.~07) produces a \texttt{QueryPlan}:

\begin{verbatim}
struct QueryPlan {
  id: PlanId,
  query: String,
  steps: Vec<PlanStep>,
  edges: Vec<(StepId, StepId)>,  // DAG dependencies
  budget: ExecutionBudget,
  config: PlanConfig,
}

struct PlanStep {
  id: StepId,
  kind: StepKind,        // Search, Synthesize, ToolCall, Aggregate, Branch
  tool: Option<ToolName>,
  input: StepInput,      // Template with variable interpolation
  output: StepOutput,    // Expected output schema
  depends_on: Vec<StepId>,
  parallel: bool,
  retry: RetryPolicy,
  timeout_ms: u64,
}
\end{verbatim}

\subsection{Execution Algorithm}
\label{sec:runtime:exec-algo}

\begin{algorithm}[H]
\caption{Plan Execution}
\label{alg:plan-exec}
\begin{algorithmic}[1]
\Require Plan $P$, initial state $S_0$
\Ensure Final state $S_f$ with answer
\State $S \gets S_0$, $completed \gets \varnothing$
\State $ready \gets \{ s \in P.steps \mid s.depends\_on \subseteq completed \}$
\While{$ready \neq \varnothing$}
  \If{$\exists s \in ready: s.parallel$}
    \State $batch \gets \{ s \in ready \mid s.parallel \}$
    \State $results \gets \textsc{ExecuteParallel}(batch, S)$
  \Else
    \State $s \gets \textsc{Pop}(ready)$
    \State $results \gets \textsc{ExecuteStep}(s, S)$
  \EndIf
  \State $S \gets \textsc{UpdateState}(S, results)$
  \State $completed \gets completed \cup \{s.id \mid s \in batch \lor s\}$
  \State $ready \gets \{ s \in P.steps \setminus completed \mid s.depends\_on \subseteq completed \}$
  \State \textsc{CheckBudget}(S, P.budget) \Comment{May raise BudgetExceeded}
  \State \textsc{EmitProgress}(S, completed) \Comment{Stream update}
\EndWhile
\State \Return $S$
\end{algorithmic}
\end{algorithm}

\subsection{Step Kinds}
\label{sec:runtime:step-kinds}

\begin{itemize}
  \item \texttt{Search}: Invoke hybrid search + evidence gate (Vol.~04)
  \item \texttt{Synthesize}: Select verified evidence under budget, render WC/1, call LLM, resolve citations, stream tokens
  \item \texttt{ToolCall}: Invoke registered tool (see \S\ref{sec:runtime:tools})
  \item \texttt{Aggregate}: Merge results from parallel branches
  \item \texttt{Branch}: Conditional execution based on prior result
\end{itemize}

\section{Evidence Context Assembly}
\label{sec:runtime:context-assembly}

\texttt{Synthesize} does not accept an arbitrary string assembled by the
planner. It accepts verified evidence records and delegates prompt construction
to a deterministic context builder:
\begin{enumerate}
  \item return \texttt{REFUSE} immediately when the evidence gate is empty;
  \item select a subset under the remaining token budget (score-ordered top-$k$
        by default; experimental concept-coverage packing only when enabled);
  \item serialize the subset through \texttt{WC/1}, preserving evidence text
        verbatim and retaining the integer-ID resolution map in host state;
  \item invoke the provider-specific LLM client with the cacheable contract
        prefix separated from the query-specific suffix;
  \item resolve cited IDs to source occurrences and run post-generation claim
        support and evidence-coverage checks (Vol.~04
        \S\ref{sec:retrieval:synthesis}).
\end{enumerate}

The context builder is provider-agnostic. Providers that expose explicit prompt
cache controls may pin the fixed \texttt{WC/1} prefix; providers that cache
implicitly still benefit from byte stability. Contract evolution is append-only
within a version so the longest common prefix remains stable. An unknown
version or failed capability negotiation takes the JSON fallback path.

\begin{verbatim}
struct EvidenceContext {
  wire_version: "WC/1",
  cache_prefix: String,
  query_suffix: String,
  id_map: HashMap<u32, EvidenceOccurrence>,
  prompt_tokens: usize,
  context_budget: usize,
}
\end{verbatim}

The \texttt{id\_map} never crosses the model boundary. It is retained in
\texttt{ExecutionState} until citation verification completes, then emitted in
the trace as the exact model-handle to source-span resolution used for the
answer. This gives citation replay a stable, auditable boundary without sending
UUIDs to the model.

\section{Hierarchical Conversation Memory}
\label{sec:runtime:conversation-memory}

Long-lived Discord channels are not reconstructed by resending their full
history. The runtime maintains a slow, durable event tier and a small,
model-visible memory tier, following recursive summarisation and external-memory
designs \citep{wang2023recursive,packer2023memgpt,yin2024twostage}:
\[
M_{n+1}
=
\operatorname{Summarize}
\left(
M_n,\,
E_{(s_n,s_{n+1}]},\,
\operatorname{Retrieve}(q)
\right).
\]
$M_n$ is the prior project or channel memory, $s_n$ is the last successfully
committed summary checkpoint, and $E_{(s_n,s_{n+1}]}$ is only the newly observed
event interval. The checkpoint advances after the summary files are durably
written. A provider failure therefore retries the same interval rather than
silently dropping discussion.

Discord message bodies and attachment text are untrusted prompt data. They may
be summarized as evidence but cannot redefine the system policy, invoke tools,
or authorize mutations. Summaries preserve
\texttt{discord:<channel>:<message>} citations and are written as separate
projections for decisions, tasks, unresolved questions, and recent activity.
The provider interface permits either a local model or the OpenAI Responses API;
the authoritative journal, lexical search, and Markdown export remain available
without either provider.

\section{Budget as Allocation, Not Truncation}
\label{sec:runtime:allocation}

The budget tracker of \S\ref{sec:runtime:budget} is a circuit breaker: it observes consumption and terminates when a limit is crossed. It never influences \emph{which} work is done, only when work stops. Under a binding budget this is close to the worst available policy, because the steps that happen to be scheduled early consume the budget regardless of their value, and the terminating action --- truncate, partial, error --- degrades an answer that a different ordering might have completed.

Time-domain astronomy operates permanently in this regime and does not treat it as an error condition. The Vera C.\ Rubin Observatory's survey will produce on the order of $10^4$ transient alerts per night against spectroscopic follow-up capacity of order $10^1$; the deficit is four orders of magnitude and is structural, not a provisioning failure. The response is a broker layer that ranks candidates in real time under hard resource constraints. \citet{aas2rto2025} score candidates and fold in observability to produce a continually updated priority list; the Fink broker applies real-time active learning to select the follow-up that most improves classification rather than the one with the highest current score \citep{fink2025active}; and \citet{rlfollowup2025} formulate follow-up scheduling as an online resource-constrained problem solved by reinforcement learning.

The third of these is the important one. Ranking by score selects what the system already believes; ranking by expected information gain selects what would change its belief.

\begin{designprinciple}[Budget Allocation over Budget Enforcement]
The execution budget is an allocation problem solved continuously during execution, not a limit checked after the fact. Steps compete for budget on expected evidential gain per unit cost, and the enforcement action is the degenerate case reached when no step clears the bar.
\end{designprinciple}

\begin{definition}[Evidential Value Density]
\label{def:value-density}
For a candidate step $s$ with estimated cost $c(s)$ in budget units, let $\Delta H(s)$ be the expected reduction in uncertainty over the answer induced by executing $s$. The value density is $\nu(s) = \Delta H(s) / c(s)$.
\end{definition}

Uncertainty here is not a free parameter: the evidence gate already produces a calibrated quantity. Using the false alarm rates of \S\ref{sec:retrieval:far}, the current evidence set induces a distribution over admissible answers, and $\Delta H(s)$ is estimated as the expected decrease in its entropy --- the step most worth taking is the one whose result is least predictable from what is already verified.

\begin{algorithm}[H]
\caption{Budget-Aware Step Scheduling}
\label{alg:budget-scheduling}
\begin{algorithmic}[1]
\Require Plan DAG $P$, budget $B$, state $S$
\Ensure Answer or partial result with accounting
\State $F \gets \textsc{ReadyFrontier}(P, S)$ \Comment{Steps with satisfied dependencies}
\While{$F \neq \varnothing$ and $B$ not exhausted}
  \ForAll{$s \in F$}
    \State $\hat{c}(s) \gets \textsc{EstimateCost}(s)$ \Comment{From historical step statistics}
    \State $\widehat{\Delta H}(s) \gets \textsc{EstimateGain}(s, S)$ \Comment{Entropy of answer distribution}
  \EndFor
  \State $s^* \gets \arg\max_{s \in F} \widehat{\Delta H}(s) / \hat{c}(s)$
  \If{$\widehat{\Delta H}(s^*) < \delta_{\min}$}
    \State \textbf{break} \Comment{No step justifies its cost; stop early and under budget}
  \EndIf
  \State $S \gets \textsc{Execute}(s^*, S)$; $B \gets B - \textsc{ActualCost}(s^*)$
  \State $F \gets \textsc{ReadyFrontier}(P, S)$ \Comment{Re-plan: results may prune or add steps}
\EndWhile
\State \Return \textsc{Synthesize}($S$), \textsc{BudgetReport}($B$)
\end{algorithmic}
\end{algorithm}

Two consequences distinguish this from enforcement. First, the loop can terminate \emph{under} budget when no remaining step earns its cost, which a circuit breaker never does --- it spends everything it is given. Second, when the budget does bind, what survives is the highest-value-density prefix rather than an arbitrary prefix, so the partial result is the best obtainable at that price rather than whatever happened to run first.

\begin{observation}[Estimator Quality Bounds the Gain]
\label{obs:estimator-quality}
Algorithm~\ref{alg:budget-scheduling} is only as good as $\widehat{\Delta H}$ and $\hat{c}$. Cost estimation is tractable, since step costs are empirically regular and improve with logged history. Gain estimation is genuinely hard and a poor estimator degrades the schedule toward arbitrary ordering --- which is to say, toward the behaviour of the circuit breaker it replaces. The failure mode is therefore bounded below by the previous design, which is why the allocation policy can be deployed incrementally.
\end{observation}

\section{Streaming Protocol}
\label{sec:runtime:streaming}

API uses Server-Sent Events (SSE) over HTTP or WebSocket:

\begin{verbatim}
# Event types
event: plan_start     { "plan_id": "...", "steps": N }
event: step_start     { "step_id": "...", "kind": "Search" }
event: step_progress  { "step_id": "...", "progress": 0.5, "details": "..." }
event: evidence       { "unit_id": "...", "relevance": 0.94, "preview": "..." }
event: token          { "token": "the", "step_id": "..." }
event: step_complete  { "step_id": "...", "output": {...} }
event: plan_complete  { "answer": "...", "citations": [...], "usage": {...} }
event: error          { "step_id": "...", "error": "..." }
event: budget_warning { "type": "tokens", "used": 80000, "limit": 100000 }
\end{verbatim}

Clients can render progressive UI: show plan, show evidence as it arrives, stream answer tokens.

\section{Error Handling and Retries}
\label{sec:runtime:errors}

\begin{itemize}
  \item \textbf{Transient errors} (network, timeout): Retry per step policy (exponential backoff)
  \item \textbf{Tool errors}: Captured in \texttt{StepResult.error}, execution continues if step not critical
  \item \textbf{LLM errors}: Rate limit $\to$ backoff; context overflow $\to$ truncate/summarize history
  \item \textbf{Budget exceeded}: Emit \texttt{budget\_warning}, then \texttt{plan\_complete} with partial answer
  \item \textbf{Fatal errors}: Invalid plan, OOM, provider unavailable $\to$ abort with error event
\end{itemize}

\section{Conversation Management}
\label{sec:runtime:conversation}

Multi-turn conversations maintain history in \texttt{ExecutionState.conversation}. The planner can reference prior turns for context. History is pruned to fit budget (summarize old turns, keep recent).

\section{Summary}
\label{sec:runtime:summary}

The Agent Runtime executes query plans as deterministic, budgeted, observable tool orchestrations:
\begin{enumerate}
  \item \textbf{Plan executor}: DAG-aware, parallel-capable, topological
  \item \textbf{Tool system}: Schema-contracted, streamable, extensible
  \item \textbf{LLM abstraction}: Multi-provider, local-first, token-aware
  \item \textbf{State}: Scratchpad, evidence accumulator, budget tracker
  \item \textbf{Context assembly}: Verified-evidence selection, WC/1 rendering, host-side citation map
  \item \textbf{Streaming}: SSE/WebSocket with fine-grained event types
  \item \textbf{Budgets}: Value-density allocation plus hard limits with graceful degradation
\end{enumerate}
The runtime is the ``CPU'' of LLMWiki; the Query Planner (Vol.~07) is the compiler that generates its instruction sequences.
