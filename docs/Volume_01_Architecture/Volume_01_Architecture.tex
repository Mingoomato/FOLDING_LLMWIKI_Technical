\chapter{Architecture}
\label{cha:architecture}

LLMWiki is not a Retrieval-Augmented Generation (RAG) framework. It is a \textbf{semantic operating layer} that continuously transforms heterogeneous digital artifacts into an evidence-aware knowledge space. This volume establishes the architectural foundations: the three-layer decomposition, the filesystem-as-WAL principle, the data flow invariants, and the module interface contracts that all subsequent volumes build upon.

\section{Design Philosophy}
\label{sec:architecture:philosophy}

\begin{designprinciple}[Source Artifacts and Event Log are Authoritative]
Two things in LLMWiki are authoritative, and nothing else is. The user's source artifacts (files, API responses, database rows) are the authoritative content. The append-only mutation/event log in \texttt{.llmwiki/wal/} is the authoritative history of every change derived from them. Everything else the system maintains---semantic units, the property knowledge graph, the vector index, the BM25 index---is a \emph{projection}: a materialized, rebuildable view computed by replaying the event log. A projection can be deleted and regenerated from the log without loss; the log itself cannot.
\end{designprinciple}

\begin{designprinciple}[Graph as Canonical Query-Time Representation]
Among the projections, the property knowledge graph is the canonical representation for query-time reasoning: it is what the query planner and evidence gate query first, and vector/keyword indices exist to accelerate or widen that graph-centric retrieval. ``Canonical'' here is a statement about which projection query execution treats as primary, not a claim about durability---durability is the event log's job (previous principle), not the graph's.
\end{designprinciple}

\begin{designprinciple}[Evidence Gate as First-Class Module]
Retrieval results must pass a mandatory cross-encoder verification stage before synthesis. This is not a reranker; it is an evidence filter with calibrated confidence thresholds.
\end{designprinciple}

\begin{designprinciple}[Local-First, LLM-Optional]
All critical-path operations (parsing, chunking, embedding, graph update, indexing, evidence verification) run locally with zero external API dependencies. LLMs are used only for planning, entity extraction (optional), and answer synthesis.
\end{designprinciple}

\begin{designprinciple}[Content Addressability]
Every semantic unit is identified by SHA-256 of its canonical form. Identical content implies identical identifier across all indices, enabling deduplication, caching, and verifiable lineage.
\end{designprinciple}

\begin{designprinciple}[Incremental Consistency]
After any ingestion, the system state (G, I, U) - graph, index, units - satisfies: a query executed against the live state produces the same result as replaying the ingestion log.
\end{designprinciple}

\begin{designprinciple}[Deterministic Replay]
Given identical .llmwiki/ directory and identical query q, two executions produce bitwise-identical results (modulo non-deterministic LLM sampling, which is confined to planning/synthesis).
\end{designprinciple}

\subsection{Layer 1: Ingestion Pipeline}
\label{sec:arch:ingestion}
Responsible for parsing heterogeneous artifacts into semantic units - content-addressed, typed, and annotated fragments. Modules:
\begin{itemize}
  \item Semantic Parser (Vol. 02): Language-aware parsing (code, markdown, PDF, OpenAPI, SQL DDL, etc.)
  \item Chunker: Hierarchical, structure-aware segmentation with overlap control
  \item Embedder: Local embedding models (BGE, E5, nomic-embed) with batch inference
\end{itemize}

\subsection{Layer 2: Core Knowledge Space}
\label{sec:arch:core}
The persistent, queryable knowledge representation. Three tightly coupled modules:
\begin{itemize}
  \item Knowledge Graph (Vol. 03): Property graph with typed nodes/edges, entity resolution, and incremental updates
  \item Semantic Index (Vol. 03): Hybrid index (HNSW vector + BM25 keyword + graph adjacency)
  \item Evidence Gate (Vol. 06): Cross-encoder verification + citation extraction + confidence calibration
\end{itemize}

\subsection{Layer 3: Query and Execution}
\label{sec:arch:query}
Composable query execution with planning and observability:
\begin{itemize}
  \item Query Planner (Vol. 07): DAG-based plan compilation, cost-based optimization, subquery decomposition
  \item Agent Runtime (Vol. 05): Tool execution, state management, streaming responses
  \item API Gateway (Vol. 08): REST/gRPC/WebSocket contracts, authentication, rate limiting
\end{itemize}

\section{Filesystem as Event Log, Projections as Derived State}
\label{sec:architecture:filesystem-wal}

\begin{designdecision}
\label{dec:fs-as-wal}
\textbf{Decision:} Use the local filesystem (directory structure .llmwiki/) to host an append-only event log as the sole durability mechanism, instead of a dedicated log service (e.g., Kafka, Redis Streams, WAL-G). The graph, vector, and keyword indices are projections computed from that log and carry no durability obligation of their own.
\end{designdecision}

\begin{designrationale}
\begin{enumerate}
  \item Zero operational dependency: No separate service to deploy, monitor, or backup.
  \item Deterministic replay: replaying \texttt{wal/} from empty projections reproduces graph/index state exactly (Algorithm~\ref{alg:ingestion}, \S\ref{sec:architecture:crash-consistency}).
  \item Content-addressed deduplication: Units stored as units/<hash>.json are naturally deduplicated.
  \item Backup equals copy: tar, rsync, borg, restic work natively on the log; projections do not need to be backed up at all, only rebuilt.
\end{enumerate}
\end{designrationale}

\begin{designtradeoff}
\begin{itemize}
  \item Concurrency: Single-writer per repository; multi-writer requires external locking (file lock or SQLite WAL mode).
  \item Scale: Directory entry count grows with unit count. Mitigation: sharded subdirectories (units/ab/cd/ef...).
  \item Durability: fsync on commit; configurable \texttt{sync\_on\_write} flag.
  \item Replay cost: rebuilding graph/vector/keyword projections from a long log is $O(\text{log length})$, not $O(1)$; \S\ref{sec:architecture:crash-consistency} amortizes this with periodic checkpoints.
\end{itemize}
\end{designtradeoff}

\subsection{Directory Layout}
\label{sec:arch:fs-layout}

\begin{verbatim}
.llmwiki/
|-- wal/                      # AUTHORITATIVE: append-only event log (JSONL)
|   |-- 2024-01-15-001.jsonl  # Each event carries a monotonic sequence number
|   |-- ...
|-- units/                    # PROJECTION: content-addressed semantic units
|   |-- ab/cd/ef1234.json     # SHA-256 prefix sharding
|   |-- ...
|-- graph/                    # PROJECTION: knowledge graph, rebuildable from wal/
|   |-- nodes/                # Node partitions (by type)
|   |-- edges/                # Edge partitions (by relation type)
|   |-- indexes/              # Graph-local indexes (adjacency, labels)
|   |-- _projection.meta      # last_applied_sequence, projection schema version
|-- index/                    # PROJECTION: semantic search indexes, rebuildable from wal/
|   |-- hnsw/                 # HNSW vector index (disk-backed)
|   |-- bm25/                 # BM25 inverted index (tantivy)
|   |-- adjacency/            # Graph adjacency for traversal
|   |-- _projection.meta      # last_applied_sequence, projection schema version
|-- checkpoints/               # Periodic full-projection snapshots (bound replay cost)
|   |-- 0000042000/            # Snapshot at wal sequence 42000
|-- planner/                  # Query plan cache
|   |-- plans/
|-- evidence/                 # Evidence gate caches
|   |-- cross-encoder/
|-- config.toml               # Repository configuration
\end{verbatim}

Every entry under \texttt{graph/} and \texttt{index/} is disposable: deleting the directory and replaying \texttt{wal/} from the last \texttt{checkpoints/} snapshot regenerates it. Only \texttt{wal/} (and the original source artifacts, which live outside \texttt{.llmwiki/}) must never be treated as disposable.

\subsection{Ingestion Pipeline}
\label{sec:arch:ingestion-pipeline}

\begin{algorithm}[H]
\caption{Ingestion Pipeline (event-sourced)}
\label{alg:ingestion}
\begin{algorithmic}[1]
\Require Artifact A (file, API response, database row)
\Ensure Event $e$ durably committed at sequence $n$; projections eventually consistent with $n$
\State U = Parse(A) \Comment{Language-aware parser}
\State U = Chunk(U) \Comment{Hierarchical, overlap-controlled}
\State Delta G = ExtractEntitiesRelations(U) \Comment{Local LLM or rule-based}
\State Delta I = Embed(U) \Comment{Batch local inference}
\State $e$ = MakeEvent(U, Delta G, Delta I) \Comment{state = PREPARED}
\State $n$ = AppendWAL($e$) \Comment{Atomic durable append; state $\to$ COMMITTED (\S\ref{sec:architecture:crash-consistency})}
\State ApplyGraph($e$, $n$) \Comment{Idempotent; no-op if graph.last\_applied\_sequence $\geq n$}
\State ApplyIndex($e$, $n$) \Comment{Idempotent; no-op if index.last\_applied\_sequence $\geq n$}
\State \Return U, Delta G, Delta I \Comment{Event state $\to$ PROJECTED once both projections advance past $n$}
\end{algorithmic}
\end{algorithm}

A query is answerable as soon as step 6 (COMMITTED) completes; it does not wait for step 9 (PROJECTED). Between those steps the event is durable but not yet reflected in graph/index reads, which is the ordinary read-after-write lag of an event-sourced system, not a correctness gap---\S\ref{sec:architecture:crash-consistency} makes precise what a reader is guaranteed to see at each stage.

\subsection{Query Pipeline}
\label{sec:arch:query-pipeline}

\begin{algorithm}[H]
\caption{Query Execution Pipeline}
\label{alg:query}
\begin{algorithmic}[1]
\Require Query q, context budget B, evidence threshold tau
\Ensure Answer a with citations C
\State $P$ = Plan($q$) \Comment{Planner outputs DAG of subqueries}
\State $R = \emptyset$
\ForAll{subquery $s$ in $P$}
  \State $R_s$ = HybridRetrieve($s$) \Comment{Vector + BM25 + Graph}
  \State $R = R \cup R_s$
\EndFor
\State E = EvidenceGate(R, tau) \Comment{Cross-encoder verify}
\If{$E = \emptyset$}
  \State \Return Refuse(``insufficient evidence'')
\EndIf
\State $E_B$ = SelectContext(E, B) \Comment{Top-$k$ default; budgeted coverage experimental}
\State $(W, M)$ = SerializeWCOne($q$, $E_B$) \Comment{Verbatim evidence + host-side id map}
\State $a$ = Synthesize($W$) \Comment{LLM cites small integer handles}
\State $C$ = ResolveCitations($a$, $M$) \Comment{Handle $\to$ occurrence and source span}
\State $a'$ = VerifyClaims($a$, $C$) \Comment{Claim support + evidence coverage}
\State \Return $a'$, $C$
\end{algorithmic}
\end{algorithm}

\section{Evidence Context Boundary}
\label{sec:architecture:evidence-context}

The evidence gate decides \emph{which units are admissible}; it does not decide
how the surviving set consumes the reader's finite context. LLMWiki therefore
places a narrow evidence-context boundary between verification and synthesis:
\begin{equation}
\mathcal{R}
\xrightarrow{\text{time scope}}
\mathcal{R}_t
\xrightarrow{\mathcal{G}_\tau}
\mathcal{E}
\xrightarrow{\text{select under } B}
\mathcal{E}_B
\xrightarrow{\text{WC/1}}
(W,M).
\end{equation}
$W$ is the model-visible prompt payload and $M$ is a host-only map from small
integer handles to \texttt{(content\_id, occurrence\_id, document, span)}.
The order is invariant: selection never precedes verification and cannot turn
an empty gate result into an answer.

\begin{designprinciple}[Compress the Envelope, Preserve the Evidence]
Only repeated metadata and machine identifiers are removed from the model-visible
envelope. Evidence text is transmitted verbatim. A transport optimisation may
reduce token cost but may not weaken human auditability, citation resolution,
or deterministic replay.
\end{designprinciple}

\paragraph{WC/1 transport.}
The line-oriented \texttt{WC/1} contract groups blocks by source document,
replaces UUIDs with response-local integer handles, and line-count-prefixes each
block so arbitrary Markdown and source code remain unambiguous. The fixed
contract instruction is query-independent and eligible for prompt-prefix
caching. The reference implementation measures total-prompt reductions of
30.3\% (English) and 32.8\% (Korean) against the equivalent JSON fallback on
cold prompts, including the fixed prefix; cached-prefix measurements are
31.7\% and 36.6\%. These are tokenizer measurements, not answer-quality results.

\paragraph{Budgeted selection.}
When verified evidence exceeds $B$, the production-safe baseline remains
score-ordered top-$k$. A deterministic reference packer instead maximises
weighted concept coverage per token with a singleton guard, following budgeted
submodular selection \citep{lin2010budgeted,peng2025adagres,bala2026survives}.
Its exploratory fixture improves the proxy objective under tight budgets, but
coverage is not answer quality; it cannot replace top-$k$ until the
\texttt{(JSON, WC/1)} $\times$ \texttt{(top-k, packed)} model A/B in
Vol.~06 succeeds.

\paragraph{Integration status.}
\texttt{eval/scripts/wire\_contract.py} and
\texttt{eval/scripts/evidence\_packer.py} are executable reference components
with deterministic tests. They are not yet called by the BM25-only
\texttt{run\_eval.py} scaffold or by a production runtime. Unknown contract
versions and failed capability negotiation fall back to JSON at the host
boundary rather than guessing.

\section{Crash Consistency and Recovery}
\label{sec:architecture:crash-consistency}

Algorithm~\ref{alg:ingestion} has three commit points (AppendWAL, ApplyGraph, ApplyIndex) that are not a single atomic transaction. A process can be killed between any two of them. This section specifies what a killed process leaves behind and how a subsequent process recovers it, so that ``the WAL is authoritative'' (design principle, \S\ref{sec:architecture:philosophy}) is a checkable property rather than an aspiration.

\subsection{Event Lifecycle}
Every event $e$ carries a monotonically increasing sequence number $n$, assigned at append time, and passes through three states:
\begin{itemize}
  \item \textbf{PREPARED}: $e$ is constructed in memory; not yet durable. A crash here loses nothing observable---the event never existed from any reader's perspective.
  \item \textbf{COMMITTED}: $e$ is durably appended to \texttt{wal/} under sequence $n$. From this point, $e$ is part of the authoritative history and \emph{must} eventually be reflected in every projection, even if the process that wrote it never runs again.
  \item \textbf{PROJECTED}: every projection $p$ (graph, HNSW, BM25) satisfies $p.\text{last\_applied\_sequence} \geq n$.
\end{itemize}
A reader asking ``is my write visible'' is asking whether the relevant projections have reached PROJECTED for that event's sequence, not whether the event is COMMITTED---these are different questions, and the API layer (Vol.~08) reports both.

\subsection{Idempotent, Resumable Projection}
Each projection directory (\texttt{graph/}, \texttt{index/}) carries a \texttt{\_projection.meta} file recording its own \texttt{last\_applied\_sequence} and a schema/projection-logic version. ApplyGraph($e$, $n$) and ApplyIndex($e$, $n$) first check this marker: if $n \leq \text{last\_applied\_sequence}$, the call is a no-op. This makes re-application safe after a crash, a redeploy, or an operator manually re-running \texttt{ApplyIndex} on a range of sequences---the operation is idempotent by construction, not by convention.

\subsection{Crash Recovery Scanner}
On startup, LLMWiki runs a recovery scan before serving queries:
\begin{enumerate}
  \item Read \texttt{last\_applied\_sequence} from every projection's \texttt{\_projection.meta}.
  \item Let $n_{\min}$ be the smallest such value across all projections (the least-caught-up projection).
  \item Replay \texttt{wal/} events with sequence $> n_{\min}$ against every projection whose marker is behind. Because application is idempotent (\S above), projections that were already ahead of $n_{\min}$ simply no-op on events they've already applied.
  \item If \texttt{wal/} has been compacted past $n_{\min}$ (a checkpoint boundary), recovery starts from the nearest \texttt{checkpoints/} snapshot at or before $n_{\min}$ instead---this is the case Invariant~\ref{inv:replay-degradation} (\S\ref{sec:architecture:lineage}) requires to be reported explicitly if the snapshot itself is missing or corrupt, rather than silently skipped.
\end{enumerate}
This scanner is what makes the directory-layout claim in \S\ref{sec:arch:fs-layout} (``every entry under \texttt{graph/} and \texttt{index/} is disposable'') literally true rather than aspirational: deleting a projection directory is equivalent to setting its \texttt{last\_applied\_sequence} to that of the nearest checkpoint, and the scanner rebuilds it on next startup.

\subsection{Atomic Commit: POSIX and Windows}
Step 6 of Algorithm~\ref{alg:ingestion} (AppendWAL) requires that a single event either becomes fully durable or leaves no trace---no torn writes. The mechanism differs by platform and neither reduces to a bare \texttt{rename(2)} call:
\begin{itemize}
  \item \textbf{POSIX (Linux, macOS):} write the event to a temp file in the same directory as the target WAL segment, \texttt{fsync} the temp file, \texttt{rename(2)} it into place (atomic within a filesystem, per POSIX), then \texttt{fsync} the containing directory so the rename itself is durable across a power loss---the directory fsync is the step most implementations omit and is required for the atomicity guarantee to survive a crash, not just a process kill.
  \item \textbf{Windows (NTFS):} \texttt{MoveFileEx} with \texttt{MOVEFILE\_REPLACE\_EXISTING} provides the rename step, but NTFS does not guarantee the same crash-durability semantics as POSIX \texttt{rename} without an explicit flush; LLMWiki additionally calls \texttt{FlushFileBuffers} on the temp file before the move and, where available, opens the target directory handle to flush metadata after it. Folding's local-first deployment target includes Windows, so this path is exercised in CI, not treated as a POSIX-only afterthought.
  \item In both cases, a segment is appended to, never modified in place; only the temp-file-then-move step is atomic, and it is used solely to publish a new immutable segment or checkpoint, never to edit an existing one.
\end{itemize}

\subsection{What Live-Copy Backups Do Not Give You}
Copying \texttt{.llmwiki/} with \texttt{rsync} or \texttt{git} while the process is running (as \S\ref{sec:architecture:filesystem-wal}'s rationale claims for backups) is safe for \texttt{wal/} segments, because segments are immutable once published and the copy tool sees either the whole segment or none of it. It is \emph{not} safe as a substitute for a consistent snapshot of \texttt{graph/} or \texttt{index/}: RocksDB, HNSW, and Tantivy each maintain multi-file on-disk structures that are only mutually consistent at their own checkpoint boundaries, and a naive directory copy taken mid-write can capture a torn cross-file state that neither the old nor the new version can open. LLMWiki therefore exposes a \texttt{snapshot()} API that requests a consistent checkpoint from each store (RocksDB checkpoint API, HNSW/Tantivy segment-boundary flush) and only then is the result eligible for \texttt{checkpoints/}; ordinary backup tools should target \texttt{wal/} plus the most recent \texttt{checkpoints/} entry, not a live copy of \texttt{graph/} or \texttt{index/}.

\section{Core Invariants}
\label{sec:architecture:invariants}

\begin{invariant}[Content Addressability]
\label{inv:content-address}
Forall u in U: id(u) = SHA256(canonical(u)). Identical content implies identical identifier across all indices.
\end{invariant}

\begin{invariant}[Evidence Closure]
\label{inv:evidence-closure}
Forall a in Answers: citations(a) subset of U and forall c in citations(a): verify(c) >= tau.
\end{invariant}

\begin{invariant}[Incremental Consistency]
\label{inv:incremental}
For every projection $p \in \{G, I, U\}$ (graph, index, units) and every sequence $n$, once $p.\text{last\_applied\_sequence} \geq n$, querying $p$ yields the same result as replaying \texttt{wal/} events $1..n$ into an empty projection (\S\ref{sec:architecture:crash-consistency}). This is a per-projection, per-sequence statement, not a claim that $G$, $I$, and $U$ are mutually synchronized at every instant---they advance independently and the recovery scanner is what reconciles them after a crash.
\end{invariant}

\begin{invariant}[Local-First Determinism]
\label{inv:local-determinism}
Given identical .llmwiki/ directory and identical query q, two executions produce bitwise-identical results (modulo non-deterministic LLM sampling, which is confined to planning/synthesis).
\end{invariant}

\section{The Filesystem as Lineage Recorder}
\label{sec:architecture:lineage}

Invariants~\ref{inv:incremental} and \ref{inv:local-determinism} assert that history can be replayed. They do not say how history is \emph{reconstructed} when the record is incomplete, and every long-lived deployment produces an incomplete record: WAL segments are compacted, old snapshots are pruned, repositories are cloned from a mid-life state. A replay guarantee that holds only over an unbroken log is a guarantee that expires.

Developmental biology has spent a decade on exactly this reconstruction problem. CRISPR lineage recorders accumulate irreversible edits at engineered target sites across cell divisions, so that the division history of an organism can be inferred from the barcodes of its terminal cells alone --- the intermediate states are gone, and the tree is recovered from the endpoint. Recent surveys note that recorders which log a \emph{deterministic temporal ordering} of mutations enable precise reconstruction of deep lineages \citep{lineagetracing2026}, which is precisely the argument for an append-only WAL. More usefully, the field has formalised inference under a degraded record: Bayesian phylodynamic frameworks reconstruct lineage trees with calibrated uncertainty from barcode data with dependent target sites and missing observations \citep{phylodynamic2025}.

Two failure modes from that literature transfer to LLMWiki without modification.

\paragraph{Homoplasy.} An identical edit arising independently in two lineages falsely implies shared ancestry. Content addressability (Invariant~\ref{inv:content-address}) makes this endemic rather than occasional: two units produced by unrelated derivation paths that happen to canonicalise identically receive the same identifier \emph{by design}. This is the deduplication property, and it is desirable for storage and indexing. It is also destructive of provenance, because it collapses distinct derivations into one node. Identity and ancestry are different relations and must not share a key.

\begin{invariant}[Lineage Distinctness]
\label{inv:lineage-distinct}
Content identity does not imply derivation identity. For a unit $u$, $\text{id}(u)$ addresses content; the derivation of $u$ is recorded separately as the set of WAL edges producing it. Provenance is therefore a directed acyclic graph over content identifiers, never a tree, and a query for the origin of $u$ returns a set of derivations rather than a unique parent.
\end{invariant}

\paragraph{Dropout.} A target site that fails to be read yields a missing character, not a wrong one, and treating the two alike corrupts the tree. The analogue is a compacted WAL segment: the derivation edge is unobserved, not absent. Recording compaction boundaries explicitly lets reconstruction distinguish \emph{no derivation occurred} from \emph{the derivation is unobservable}, which is the difference between a false claim and an honest one.

\begin{invariant}[Replay Degradation is Explicit]
\label{inv:replay-degradation}
Where the WAL has been compacted, replay returns a result annotated with the reconstruction's uncertainty rather than an unqualified answer. A deployment that cannot verify a replay reports that it cannot, and never silently substitutes a plausible history.
\end{invariant}

This is the mechanism that makes the auditability claim survive contact with operations. A system that guarantees reproducibility only while nothing has been pruned has guaranteed reproducibility only in the laboratory; the useful statement is that reproducibility degrades in a declared, measurable way.

\section{Patent-Relevant Novelty}
\label{sec:architecture:patent}

\begin{patentclaim}
\textbf{Claim 1:} A semantic operating layer characterized by: (a) content-addressed semantic units stored in a filesystem-backed write-ahead log, (b) a property knowledge graph as the canonical knowledge representation, (c) a hybrid semantic index combining vector, keyword, and graph adjacency, (d) an evidence gate that verifies retrieval results via cross-encoder scoring before synthesis, and (e) a DAG-based query planner that decomposes queries into verifiable subqueries.
\end{patentclaim}

\begin{patentclaim}
\textbf{Claim 2:} The system of Claim 1 wherein the filesystem serves as the sole durability mechanism, enabling deterministic replay via directory synchronization without auxiliary transaction logs.
\end{patentclaim}

\begin{patentclaim}
\textbf{Claim 3:} The system of Claim 1 wherein the evidence gate operates as a mandatory pipeline stage, rejecting any retrieval result that fails cross-encoder verification against a calibrated threshold, thereby enforcing evidence closure.
\end{patentclaim}

\begin{patentdiscussion}
Prior art distinctions:
\begin{itemize}
  \item RAG (Lewis et al., 2020): Vector index is primary; no graph; no evidence gate; API-dependent.
  \item GraphRAG (Edge et al., 2024): Graph constructed via LLM; no content-addressed units; no filesystem WAL; no mandatory evidence gate.
  \item HippoRAG (Guti{\'e}rrez et al., 2024): Personalized PageRank over graph; no hybrid index; no deterministic replay.
  \item LightRAG (Guo et al., 2024): Dual-level retrieval; no evidence gate; no DAG planner.
  \item RAPTOR (Sarthi et al., 2024): Recursive summarization tree; no graph; no filesystem WAL.
  \item Zep/Graphiti (Rasmussen et al., 2025) \cite{rasmussen2025zep}: the closest prior art for temporal validity. Every edge carries a bitemporal interval (\texttt{valid\_at}/\texttt{invalid\_at}) and superseded facts are invalidated rather than deleted, so LLMWiki must \emph{not} claim validity intervals or as-of querying as novel. Distinctions: entity extraction is LLM-based, so graph construction is not reproducible from identical input; there is no mandatory evidence gate and no refusal outcome; and ingestion cost scales with LLM tokens per episode rather than CPU.
  \item Glean (Meta, 2024) \cite{meta2024glean}: revision-scoped incremental code indexing at monorepo scale (indexes the diff between a base and current revision in $O(\text{changes})$), parser-driven and therefore deterministic. This anticipates version-anchored code graphs; LLMWiki must not claim that either. Distinction: Glean is a code-intelligence index with no retrieval-refusal semantics --- there is no notion of declining to answer for want of evidence.
  \item Kythe (Google) \cite{google_kythe}: per-compilation-unit node/edge streams keyed by VName; same distinction as Glean.
\end{itemize}

\par\noindent\emph{Note on what remains after the above:} validity intervals (Zep) and version-anchored deterministic code graphs (Glean, Kythe) are each established prior art, so neither is claimed here as novel in isolation. The element without an identified antecedent is the \emph{conjunction}: an evidence gate whose refusal decision is itself scoped to a validity bound, so that ``not answerable from the corpus as of $t$'' is a reproducible first-class outcome carrying the time bound that produced it. Glean and Kythe have no refusal semantics; Zep has no gate; the GraphRAG family has no temporal axis. That conjunction is exercised by executable tests in \texttt{eval/scripts/test\_temporal\_gate.py} rather than asserted here.
\end{patentdiscussion}

\section{Summary}
\label{sec:architecture:summary}

LLMWiki's architecture is defined by six differentiating choices:
\begin{enumerate}
  \item \textbf{Graph-first, vectors-second}: The property graph is the canonical query-time representation; vectors are derived projections for similarity search.
  \item \textbf{Event log as durability layer}: Zero operational dependencies; graph/vector/keyword projections are rebuildable from the append-only log, which is the only thing that must never be lost.
  \item \textbf{Content-addressed units}: SHA-256 identities enable deduplication, caching, and verifiable lineage.
  \item \textbf{Evidence gate as mandatory stage}: No retrieval result reaches synthesis without cross-encoder verification.
  \item \textbf{DAG query planner}: Queries decompose into verifiable subqueries with cost-based optimization.
  \item \textbf{Evidence-preserving context boundary}: Verified evidence is selected under budget, transported without rewriting, and resolved back to exact source occurrences.
\end{enumerate}
These choices are not incremental improvements over RAG - they represent a different architectural category: a semantic operating layer.

The subsequent volumes detail each module's algorithms, data structures, APIs, and implementation considerations.
